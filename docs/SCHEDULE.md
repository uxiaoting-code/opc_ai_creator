## 1. 执行模式

采用 **契约先行 + 后端先行 + 前端 UI 并行 + 前端接口后接**：

```text
第 1 步：冻结用户端接口契约和状态机
        ↓
第 2 步：后端按模块实现并测试
        同时：前端只做 UI 修复和组件整理，不接未完成接口
        ↓
第 3 步：后端模块完成后 push
        ↓
第 4 步：前端逐个模块接真实接口
        ↓
第 5 步：每接完一个业务模块，双方做一次联合验收
        ↓
第 6 步：全部模块完成后做最终端到端验收
```

### 是否可以先把后端全部做完，再让搭档做前端？

**可以。** 但建议采用下面的组合，避免搭档完全闲置和最后集中爆雷：

- 你：按 M0 → M1 → M2 → M3 → M4 做完全部后端。
- 搭档：同时先做 M5 的 UI 乱码、字体、小屏和组件整理。
- 你完成一个后端模块并 push 后，搭档可以开始接该模块；也可以等你全部后端完成后再集中接。
- 不能等所有页面和所有后端最后一天才第一次联调；每个模块仍要保留一次验收。

## 4. 后端先行的详细顺序

### 第 1 阶段：M0 冻结契约（✅ 2026-10-29 已完成）

你必须先完成：

- 订单结构和状态：

```text
OPEN -> ACCEPTED -> SUBMITTED -> APPROVED / REJECTED
```

- 提交和审核结构：

```text
PENDING -> APPROVED / REJECTED
```

- 钱包规则：
  - 审核通过前不计入可提现余额；
  - 审核通过后写收入流水；
  - 提现申请先冻结金额；
  - 提现成功或失败都要更新流水；
  - 前端不自行计算最终余额。
- 错误码：
  - 未接单；
  - 重复接单；
  - 无权访问订单；
  - 重复审核入账；
  - 余额不足；
  - 提现金额非法。

**M1 已完成。下一步：推送 M1 后开始 M2 作品提交与审核。**

### 第 2 阶段：M1 订单链路（✅ 2026-10-29 已完成）

你完成：

```text
GET  /api/orders/available
GET  /api/orders/{id}
POST /api/orders/{id}/accept
GET  /api/orders/{id}/workbench
```

测试：

- 未登录不能访问；
- 同一用户不能重复接单；
- 不能接不存在/已关闭订单；
- 接单后工作台返回正确订单上下文。

M1 push 后，搭档可以先接接单大厅、订单详情、工作台。

### 第 3 阶段：M2 提交与审核

你完成：

```text
POST /api/submissions
GET  /api/submissions/my
GET  /api/submissions/{id}
GET  /api/submissions/{id}/review
```

测试：

- 没有接单不能提交；
- 提交后订单进入 `SUBMITTED`；
- 只有审核方/管理员能审核；
- 审核通过只入账一次；
- 审核驳回可重新提交。

M2 push 后，搭档接提交页、审核页和作品详情页。

### 第 4 阶段：M3 钱包

你完成：

```text
GET  /api/wallet/summary
GET  /api/wallet/transactions
GET  /api/wallet/recharge-channels
POST /api/wallet/recharges
GET  /api/wallet/withdraw-channels
POST /api/wallet/withdrawals
```

测试：

- 充值回调幂等；
- 提现不能超过可提现余额；
- 提现冻结和成功/失败状态正确；
- 审核通过收入只入账一次。

### 第 5 阶段：M4 AI 生成

你完成：

- 文生图接现有 Harness；
- 图生视频接现有 Harness；
- 音频生成新增 TTS Provider / Mock Provider；

- 任务完成后写入提交记录。

M4 完成后再做最终真实生成联调。
